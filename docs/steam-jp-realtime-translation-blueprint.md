# Steam 日本語未対応タイトル向け リアルタイム和訳オーバーレイ 設計ブループリント

**プロダクト名(仮): LiveYaku(ライブ訳)**

> **命名上の注意**: 製品名・ロゴ・ドメインに「Steam」の文字列を含めない(§8.3 商標リスク参照)。本書内では対象プラットフォームの説明としてのみ「Steam」を用いる。

対象: 日本語未対応(公式ローカライズなし)の Steam タイトルをプレイする日本語話者ユーザー
初期対象 OS: **Windows 専用**(§1.2 の確定方針)
配布形態: **個人利用中心の OSS / 無料ツール**(§1.2、§8 参照)
本書の目的: 実装は行わず、プロダクト仕様・システムアーキテクチャ・データ設計・法的セーフガード・**エラー/リスクの徹底洗い出し**・実装フェーズの AI オーケストレーション方針を定義する。

> **モデル表記について**: 本書で「Claude Fable 5」「Claude Opus」と表記する箇所は Anthropic API のモデル ID(執筆時点では各々 `claude-fable-5-1` / `claude-opus-5`。変更された場合は最新の対応モデル ID)に置き換えること。実装時の置換箇所は `{{MODEL_ID_*}}` とマークする。

## 1. プロダクト概要とコアコンセプト

### 1.1 一文で言うと

「日本語ローカライズのない Steam タイトルのゲーム内テキストを、**実行ファイル・メモリへの書き込みを一切行わない読み取り専用フック**で捕捉し、ゲーム画面上に半透明オーバーレイで日本語訳をほぼリアルタイム表示する、ブラウザ拡張 + ローカル常駐ヘルパーのハイブリッド Web アプリ」。

### 1.2 確定した設計方針(ヒアリング結果サマリー)

以下はユーザーとの選択式ヒアリングで確定した、本書全体を貫く設計上の意思決定。

| # | 論点 | 決定 | この決定が波及する箇所 |
|---|---|---|---|
| D1 | テキスト取得方式 | メモリ/プロセスフッキング(読み取り専用) | §4.3, §7-技術リスク, §8.2 |
| D2 | 表示方式 | デスクトップオーバーレイ | §4.4, §7-技術リスク |
| D3 | 全体アーキテクチャ | ブラウザ拡張 + ローカル常駐ヘルパー(Native Messaging) | §4.1, §4.2 |
| D4 | 翻訳エンジン | ハイブリッド(ローカルキャッシュ/辞書 + クラウド LLM) | §4.5, §6.4 |
| D5 | アンチチート対応 | 検出したら機能を自動無効化 + 警告表示 | §4.3.3, §7, §8.4 |
| D6 | フッキング失敗時の代替 | OCR を保険的フォールバックとして併用 | §4.3.4, §7 |
| D7 | 対象 OS(初期) | Windows 専用 | §4, §5, §10 |
| D8 | 配布形態・利用者像 | 個人利用中心の OSS / 無料ツール | §8 全体、収益モデルはスコープ外 |

### 1.3 コア原則:「読み取り専用・非改変」

法務・信頼性の両面での生命線として、以下を**アーキテクチャレベルで強制する**。

| やって良いこと | やってはいけないこと |
|---|---|
| プロセスメモリ・API 呼び出し引数の**読み取り**(文字列の観測のみ) | ゲームの実行ファイル(.exe / .dll)への書き込み・改変 |
| DirectX/OpenGL のテキスト描画 API・エンジンのテキストレンダリング関数への **API フック**(トランポリン方式、Detours 系)で引数文字列を横取り | メモリへの値の書き込み(座標・所持金・HP 等のチート行為に繋がる操作) |
| 別プロセス(自作オーバーレイウィンドウ)への描画 | ゲームプロセスのコードセグメントへのコード注入・パッチ |
| OCR によるスクリーン**読み取り** | ゲームの保存データ・オンライン通信内容の改変 |

この原則により、既存の実績あるファン翻訳ツール(Textractor、VNR 等)と同じ「読み取り専用フック」のカテゴリに設計を収め、チート行為(値の書き換え、対戦優位性の取得)とは明確に一線を画す。ただし §7・§8 で詳述する通り、**読み取り専用であっても EULA・利用規約違反やアンチチート誤検知のリスクはゼロにならない**ため、これはリスク低減策であってリスク排除策ではない。

### 1.4 想定ユーザーとユースケース

| ペルソナ | ユースケース |
|---|---|
| インディー/マイナー海外タイトル愛好者 | 日本語化 MOD が存在しない小規模タイトルを、翻訳者の作業を待たずに遊びたい |
| Early Access タイトルのプレイヤー | 頻繁にテキストが更新されるため公式/有志 MOD 翻訳が追いつかないゲームで、常に最新テキストの和訳が欲しい |
| 英語 UI に抵抗があるライトゲーマー | 高精度でなくても、メニュー・アイテム説明の大意が分かれば十分 |

## 2. ユーザーフロー

### 2.1 コンポーネント別 UI 一覧

| # | コンポーネント | 画面/UI | 主要要素 |
|---|---|---|---|
| C1 | ブラウザ拡張 | ダッシュボード(ポップアップ) | 対応ゲーム検索、ローカルヘルパーの接続状態、翻訳 ON/OFF |
| C2 | ブラウザ拡張 | ゲームプロファイル画面 | 検出済みゲーム一覧、フック方式(Hook/OCR)の表示、対応状況バッジ |
| C3 | ブラウザ拡張 | 用語集・辞書エディタ | ユーザー独自の訳語登録、既存訳の上書き |
| C4 | ブラウザ拡張 | 設定 | オーバーレイの位置・フォント・透過度、翻訳エンジン設定(API キー等)、アンチチート検知時の挙動 |
| C5 | ローカルヘルパー(常駐) | システムトレイメニュー | 現在の監視状態、ゲーム検出通知、緊急停止 |
| C6 | オーバーレイ(ゲーム画面上) | 翻訳吹き出し/字幕バー | 原文(任意表示)+ 日本語訳、フェードイン/アウト |
| C7 | ブラウザ拡張 | 診断/エラーレポート画面 | フック失敗理由、OCR フォールバック中の表示、既知の問題へのリンク |

### 2.2 導入・起動フロー(ハッピーパス)

```
[インストール]
  拡張機能(Chrome/Edge Web Store) + ローカルヘルパー(署名付きインストーラ)を導入
   ↓
[初回ペアリング] 拡張機能とローカルヘルパーを Native Messaging で接続(トークンで相互認証)
   ↓
[常駐監視開始] ローカルヘルパーが実行中プロセスを監視(ポーリング、Steam 実行パス配下を優先スキャン)
   ↓
[対象ゲーム起動検知] プロセス名/実行パスから game_profiles と照合
   ↓
   ├─ プロファイル一致 → §4.3.3 アンチチート検知 → 未検出なら [フック試行]
   │                                              → 検出なら [D5: 機能無効化+警告] → OCR設定確認へ
   ├─ プロファイル部分一致(エンジン種別のみ判明) → 汎用シグネチャでのフック試行(精度は劣る)
   └─ プロファイル未登録 → [D6: OCR フォールバックを提案] or 「未対応タイトル」表示
   ↓
[フック成功] 文字列イベントをローカルヘルパーが捕捉 → 翻訳パイプライン(§4.5)→ オーバーレイ描画(§4.4)
   ↓
[プレイ中] ゲーム内テキスト更新のたびに増分翻訳・オーバーレイ更新
   ↓
[終了検知] プロセス終了でフック/オーバーレイを自動クリーンアップ
```

**設計上の要点**

- 「対応タイトル一覧」はコミュニティ提供の `game_profiles`(§6.1)に基づくが、**未検証プロファイルの自動適用はしない**(署名/モデレーションを経たもののみ自動適用、§7 サプライチェーンリスク)。
- アンチチート検知は**プロセス起動直後・最優先**で行い、検知後のフック試行は行わない(D5 のフェイルセーフをフロー上の最初のゲートにする)。
- OCR フォールバックへの切替はユーザーに明示通知した上で行う(黙って精度の異なる方式に切り替えない)。

## 3. 機能定義: MVP / V1 / 将来バージョン

### 3.1 MVP(Windows 専用、§10 のロードマップ対象)

| 機能 | 内容 | 除外事項 |
|---|---|---|
| ローカルヘルパー基盤 | プロセス監視、Native Messaging 通信、システムトレイ UI | 自動アップデート機能なし(手動更新) |
| ゲームプロファイル照合 | プロセス名/パスベースのマッチング、エンジン種別判定(Unity/UE 系のみ) | 独自エンジンの自動プロファイリングなし |
| アンチチート検知 | 既知プロセス/サービス/ドライバ名によるブラックリスト方式 | ヒューリスティック検知なし(誤検知回避のため既知リストのみ) |
| テキストフック(Unity/UE のみ) | API フックによる文字列引数捕捉、増分差分検知 | 独自エンジン対応なし(V1 送り) |
| OCR フォールバック | 画面領域指定 + OCR(日本語対応済みゲームでの誤爆防止のため既定 OFF) | 全画面自動 OCR なし(範囲指定必須) |
| オーバーレイ描画 | ウィンドウコンポジション方式(ボーダレスウィンドウ/ウィンドウモードのみ) | 排他フルスクリーン対応なし(§7 既知の制約) |
| 翻訳パイプライン | ローカルキャッシュ(SQLite)+ Claude API(クラウド)のハイブリッド | オンデバイス LLM なし |
| 用語集 | ユーザー個人辞書(上書き翻訳) | 共有用語集/コミュニティ辞書なし |
| セーフガード UI | アンチチート検知時の強制警告モーダル、免責事項への同意フロー | — |

### 3.2 V1(MVP 安定後)

- **独自エンジン対応の拡張**: シグネチャスキャンによるオフセット自動解決、パターン更新の仕組み。
- **コミュニティプロファイル共有**: `game_profiles` のモデレーション付き共有(署名検証、悪意あるオフセット混入対策、§7 サプライチェーンリスク対応)。
- **排他フルスクリーン対応**: DXGI SwapChain Present フックによるオーバーレイ描画(RTSS/Discord オーバーレイ等と同種の技術。ただし対応ゲームごとの互換性検証コストが高い)。
- **共有用語集**: ゲームごとのコミュニティ訳語辞書(ライセンス・著作権チェック付き)。
- **翻訳品質フィードバックループ**: ユーザーの訳文修正を用語集に反映。

### 3.3 将来バージョン(V2+)

- **macOS(Proton/Crossover 経由)/ Steam Deck(Linux)対応の検討**: フック方式が Windows 前提のため設計をゼロから見直す必要あり(§4.3 の抽象化レイヤーが前提)。
- **音声読み上げ(TTS)連携**: 会話シーンでの日本語読み上げ。
- **パブリッシャー向け公式連携**: 開発元が任意でテキスト API・ローカライズファイルを提供できる「公式連携モード」(読み取り専用フックが不要になり最もリスクが低い経路)。

### 4.2 モジュール構成

| モジュール | 責務 | 主要技術 | プロセス境界 |
|---|---|---|---|
| `extension-ui` | 設定・辞書・状態表示 | React + Manifest V3 | ブラウザプロセス |
| `native-messaging-bridge` | 拡張機能⇔ローカルヘルパーの認証付き通信 | Chrome Native Messaging API | ブラウザ⇔ヘルパー間 |
| `process-monitor` | 実行中プロセスの監視、ゲーム検知 | Win32 API (ToolHelp32) | ヘルパープロセス(通常権限) |
| `anticheat-detector` | 既知アンチチートプロセス/サービス/ドライバの検知(D5) | プロセス/サービス列挙 + ブラックリスト | ヘルパープロセス |
| `profile-matcher` | `game_profiles` との照合、エンジン種別判定 | ルールエンジン | ヘルパープロセス |
| `hook-injector` | 対象プロセスへの読み取り専用 API フック注入(D1) | Detours 系トランポリンフック、DLL injection | **別ヘルパープロセス(最小権限、対象ゲームと同ユーザー権限まで)** |
| `ocr-fallback` | 指定領域のスクリーンキャプチャ + OCR(D6) | Windows Graphics Capture API + Tesseract/クラウド OCR | ヘルパープロセス |
| `translation-pipeline` | キャッシュ照合、用語集適用、クラウド LLM 呼び出し | SQLite + Anthropic API `{{MODEL_ID_TR}}` | ヘルパープロセス |
| `overlay-renderer` | 透過ウィンドウでの字幕描画 | Win32 レイヤードウィンドウ / (V1) DXGI Present Hook | **別プロセス(オーバーレイ専用、対象ゲームへの注入なし)** |
| `profile-registry-client` | プロファイル/シグネチャ DB の取得・署名検証 | HTTPS + Ed25519 署名検証 | ヘルパープロセス |
| `telemetry`(任意・opt-in) | フック成功率・エラー種別の匿名集計 | イベント送信(既定 OFF) | ヘルパープロセス |

**プロセス分離の設計意図**: `hook-injector` は対象ゲームへの注入という最もリスクの高い操作を担うため、他の機能(UI、翻訳、設定)から独立したプロセスに分離する。これにより (a) フック失敗/クラッシュが他機能に波及しない、(b) 注入コードの権限・攻撃面を最小化できる、(c) セキュリティレビュー時に監査対象を局所化できる。

### 4.3 テキスト取得パイプライン設計(詳細)

#### 4.3.1 フック方式の選定

「メモリ直接スキャン(値の総当たり探索)」ではなく、**API フック方式**を採用する。

| 方式 | 説明 | 採否 |
|---|---|---|
| **API フック(採用)** | テキスト描画 API(DirectX `DrawText` 系、エンジンのフォントレンダリング関数、`.NET`/Mono の文字列描画呼び出し等)をトランポリンフックし、呼び出し引数の文字列を読み取る | ✅ Textractor 等と同系統。読み取り専用で改変なし。エンジンの世代交代で呼び出し規約が変わるとメンテが必要 |
| メモリパターンスキャン+定期ポーリング | 既知のメモリオフセットを定期的に読み取る | △ V1 でオフセット自動解決の補助手段として限定利用。ゲームアップデートで即座に無効化されやすい |
| 生ソケット/ファイル I/O 傍受 | ネットワーク通信やローカライズファイル I/O を横取り | △ 将来検討。オンライン専用ゲームでは通信内容の傍受が利用規約上さらにグレー |

#### 4.3.2 プロファイル駆動アーキテクチャ

- `game_profiles`(§6.1)に、対象タイトルの実行ファイル名、エンジン種別、フック対象 API のシグネチャパターンを登録。
- **ハードコードされた絶対オフセットは使用しない**(ゲームアップデートのたびに壊れるため)。シグネチャ(バイトパターン)スキャンで実行時に解決する方式を基本とする。
- 未登録タイトルはエンジン種別の自動推定(実行ファイルのインポートテーブルや同梱 DLL から Unity/UE 等を判定)→ 汎用シグネチャで試行 → 失敗時は OCR フォールバックを提案。

#### 4.3.3 アンチチート検知(D5)

- プロセス監視時に既知のアンチチートプロセス名・サービス名・ロードされたドライバ(例: EasyAntiCheat 関連、BattlEye 関連の既知モジュール名)を**ブラックリスト照合**で検知する(ヒューリスティック検知は誤検知が高コストなため採用しない)。
- 検知した場合:
  1. `hook-injector` の起動そのものを行わない(フック試行前に遮断)。
  2. 拡張機能 UI に警告モーダルを表示(「このタイトルはアンチチート導入を検出したため、メモリフッキングによる翻訳を無効化しました。アカウント停止等のリスクを避けるための保護です」)。
  3. D6 に従い OCR フォールバックへの切替を提案(OCR は画面読み取りのみでプロセスへの注入を伴わないため、アンチチートの検知対象になりにくいが**ゼロリスクではない**ことも明示、§7)。
- 既知リストは `profile-registry-client` 経由で更新(署名検証必須)。

#### 4.3.4 OCR フォールバック(D6)

- ユーザーが翻訳対象の画面領域を手動指定(既定は全画面 OCR にしない。誤検知・過検出防止と処理負荷軽減のため)。
- Windows Graphics Capture API でフレームを取得 → OCR エンジンでテキスト領域検出・認識 → 翻訳パイプラインへ。
- フック方式と比べて (a) 認識精度が場面依存で不安定、(b) 文脈情報(UI 要素種別、変数プレースホルダ)が失われる、というトレードオフを UI 上で明示。

### 4.4 オーバーレイ描画パイプライン(D2)

| 方式 | 対応ウィンドウモード | メリット | デメリット | MVP 採否 |
|---|---|---|---|---|
| **レイヤードウィンドウ(WS_EX_LAYERED)方式** | ボーダレスウィンドウ / ウィンドウモード | 実装がシンプル、対象ゲームプロセスへの描画注入が不要(オーバーレイは完全に別プロセスのウィンドウ) | **排他フルスクリーンモードでは最前面に出せない**(§7 既知の制約) | ✅ MVP 採用 |
| DXGI SwapChain Present Hook | 排他フルスクリーンを含む全モード | 表示互換性が高い(RTSS/Discord オーバーレイと同種) | 対象プロセスへの DLL 注入が必須になり、フックのリスク面(§7)が Overlay にも及ぶ。ゲームごとの互換性検証コストが高い | V1 で検討 |

**MVP の運用制約として明示する**: 排他フルスクリーンで遊ぶゲームでは、ユーザー側でボーダレスウィンドウモードへの切替を案内する(多くの Steam タイトルは設定でボーダレス化可能)。この制約は隠さず、対応状況バッジ(§2.1 C2)に明示する。

### 4.5 翻訳パイプライン(D4)

```
[原文イベント] (原文, 文脈タグ: UI要素種別/会話/アイテム説明, ゲームID)
   ↓
[プレースホルダ保護] "%s" "{0}" "<color=red>" 等の変数/タグを一時トークン化して保護
   ↓
[用語集適用チェック] ユーザー辞書(C3)に完全一致があれば即時返却
   ↓
[ローカルキャッシュ照合] (game_id, 原文ハッシュ) で SQLite キャッシュを照合 → ヒットなら即時返却
   ↓ キャッシュミスのみ
[デバウンス/バッチ化] 短時間(例: 200ms)内の複数原文をまとめて1リクエスト化(API呼び出し削減)
   ↓
[Claude API 呼び出し] {{MODEL_ID_TR}}, 文脈タグ・用語集をプロンプトに注入、低温度(0.2)
   ↓
[プレースホルダ復元] 保護したトークンを訳文に復元し、破損していないか検証(§7)
   ↓
[キャッシュ書き込み] → [オーバーレイへ送信]
```

- **コスト・遅延対策**: ローカルキャッシュヒット率を最大化するため、`(game_id, 原文ハッシュ)` の正規化(空白・改行差異の吸収)を行う。
- **プレースホルダ破損検知**: 翻訳後に元のプレースホルダ数・種類が一致するかを機械チェックし、不一致ならフォールバック(原文表示 + 警告)。

## 7. エラーチェック / リスクマトリクス(本書の核心)

ユーザー指示「エラーチェックを徹底的に」に対応する中心セクション。深刻度は **致命的(Critical)/ 高(High)/ 中(Medium)/ 低(Low)**。

### 7.1 技術リスク: フッキング(D1)

| # | リスク | 深刻度 | 発生条件 | 緩和策 | 残存リスク |
|---|---|---|---|---|---|
| T1 | ゲームアップデートでフック対象 API のシグネチャが変化し、フックが無効化 or クラッシュを誘発 | High | ゲーム側の頻繁な更新(特に Early Access) | バイトパターンスキャン方式(絶対オフセット不使用)、フック前にシグネチャ整合性チェック、不一致ならフック中止(クラッシュ回避を最優先) | 更新直後は翻訳が一時的に機能しない期間が必ず発生する(設計上避けられない) |
| T2 | フック注入自体が対象ゲームをクラッシュさせる | Critical | トランポリンフックの設置箇所が想定と異なる、マルチスレッド競合 | 実績あるフックライブラリ(Detours/MinHook)使用、フック設置前後でのサニティチェック、注入は別プロセスから行い失敗時は即座にロールバック | ゼロにはできない。**フック注入前に「クラッシュのリスクがあります」の明示同意を必須化** |

|---|---|---|---|---|---|
| S1 | DLL インジェクション技術そのものがアンチウイルス/Windows Defender に「不審な挙動」として誤検知される | High | 署名なし配布、ヒューリスティック検知の強いAV | EV/OV コード署名証明書の取得、主要 AV ベンダーへの誤検知報告プロセスを整備、README で誤検知時の対処法を明示 | 誤検知の完全排除はベンダー側の判断に依存し保証不可 |
| S2 | ローカルヘルパーが不必要に高い権限(管理者権限)で動作し、侵害時の被害範囲が拡大 | High | 実装の不備で安易に管理者権限を要求 | `hook-injector` はターゲットプロセスと同一ユーザー権限の範囲で動作させ、**管理者権限を要求しない設計を原則とする**(必要な場面が生じた場合は個別に権限昇格を最小範囲・最短時間で行う) | 一部のアンチチート実装は管理者権限のフックを拒否するため機能制限が生じ得る(D5 のブラックリスト検知で事前に遮断) |
| S3 | Native Messaging Host のなりすまし・不正な拡張機能からの接続 | Medium | 拡張機能 ID を偽装した悪意あるプロセスからの接続試行 | Native Messaging のマニフェストで許可する拡張機能 ID を固定、ペアリング時にトークン相互認証 | ローカルマシンが既に侵害されている場合の防御は範囲外(OS レベルの信頼境界) |
| S4 | 注入した DLL 自体が対象ゲームプロセスの新たな脆弱性(攻撃面)になる | Medium | フック DLL のバグがメモリ破壊を引き起こす | 最小権限・最小機能の DLL(文字列読み取りとキュー投入のみ)、メモリ安全性の高い言語部分の活用検討(V1 で Rust 化を再検討) | C++ 実装である以上、メモリ安全性バグのリスクはコードレビューでの低減が主対応 |
| S5 | OCR フォールバックが意図せず機微情報(チャット欄の個人情報、ログイン画面等)をキャプチャしクラウド送信 | Medium | 範囲指定が広すぎる、ユーザーがログイン画面を含めて指定 | 範囲指定 UI での警告、既定でクラウド OCR ではなくローカル OCR(Tesseract)を使用、キャプチャ画像自体は外部送信せず抽出テキストのみパイプラインに渡す | ユーザー設定ミスに起因するリスクは UI 警告以上の技術的排除が困難 |

## 9. 開発体制: サブエージェント・オーケストレーションと AI モデル運用方針

ユーザー指示「コーディングもトークン節約を前提にオーケストレーションを活用してサブエージェントを立てつつ、複雑なタスクは Fable・Opus モデルを併用して検証を重ねる」に対応する、**実装フェーズ(本書の対象外だが後続タスクとして想定)向けの運用方針**。

### 9.1 サブエージェント分割方針

モジュール境界(§4.2)に沿って担当を分割し、各サブエージェントのコンテキストを局所化することでトークン消費を抑える。

| サブエージェント | 担当範囲 | 想定モデル | 検証頻度 |
|---|---|---|---|
| `hook-agent` | `hook-injector`(§4.3, §7 T1-T6 に直結する最重要・最高リスク領域) | **実装は高速モデル(Sonnet系)、設計判断・コードレビューは Opus で複数回検証** | 実装コミットごとに Opus レビュー必須(Critical/High リスク項目のため) |
| `overlay-agent` | `overlay-renderer`(§4.4, §7.2) | Sonnet系(実装)、DPI/マルチモニタ等のエッジケース設計は Fable で発想補助+Opus で検証 | マイルストーン単位でレビュー |
| `translation-agent` | `translation-pipeline`(§4.5, §7.3) | Sonnet系(実装)、プロンプト設計・プレースホルダ保護ロジックは Fable で複数パターン検証 | プロンプト変更のたびに回帰テスト |
| `extension-ui-agent` | ブラウザ拡張 UI(§2.1) | Sonnet系 | 通常のコードレビューのみ |
| `security-review-agent` | §7 の Critical/High 項目横断レビュー、権限設計(S1-S5)、サプライチェーン(OP1, OP3) | **Opus 固定(セキュリティクリティカル領域のため高速モデルへの切替を行わない)** | フック/権限まわりの変更全件 |

### 9.2 モデル使い分けの原則

- **通常実装(UI 実装、定型的な CRUD、既存パターンの踏襲)**: 高速・低コストモデルで実施し、トークンを温存する。
- **複雑・高リスクなタスク(§7 で Critical/High と判定した領域: フック注入、権限設計、プレースホルダ保護、アンチチート検知ロジック)**: Fable で複数の設計案を発想・比較させた上で、Opus に採用案のセキュリティ・正当性レビューをさせる**2段階検証**を必須とする。
- **検証を重ねる対象の絞り込み**: 全コードを Opus でレビューするとコストが跳ね上がるため、§7 のリスクマトリクスで Critical/High と判定された項目に対応するコードパスのみを Opus レビュー対象とし、Medium/Low 項目は通常のコードレビュー(Sonnet系)で足りるとする。この絞り込み自体が「トークン節約を前提にした」運用の核。

### 9.3 トークン節約の実装ルール

1. 各サブエージェントには担当モジュール(§4.2 の該当行)の情報のみを渡し、全体設計書を毎回丸ごと読ませない(必要な章のみ抜粋して渡す)。
2. サブエージェント間の連携は**ファイル差分(diff)またはインターフェース定義**でやり取りし、実装過程の思考ログを往復させない。
3. レビュー依頼(Opus/Fable)は「変更差分 + 関連リスク項目(§7 の該当 ID)」のみを渡し、リポジトリ全体の再読込を避ける。
4. 定型的な検証(ビルド、単体テスト、Lint)はモデル呼び出し前にツールで機械チェックし、モデルには「機械チェックを通過した差分」のみをレビューさせる。

## 12. オープンクエスチョン(次の意思決定ポイント)

実装フェーズに進む前に、追加で選択式確認が必要と考えられる論点。

1. **PoC 対象タイトルの選定**: F1 のフック PoC をどのゲーム(または自作テストビルド)で行うか。実在の商用タイトルを直接対象にするか、ライセンス的にクリーンな OSS/フリーゲームで技術検証するか。
2. **排他フルスクリーン対応(DXGI Hook)を V1 スコープに含めるか**: §7 O1 の制約が実利用上のボトルネックになりやすいため、MVP 後すぐに着手するか、コミュニティフィードバックを見て判断するかの優先順位。
3. **コミュニティプロファイル共有(OP1 のサプライチェーンリスクを伴う機能)をいつ・どの程度のモデレーション体制で解禁するか**。

これらは実装着手前に改めて選択式で確認する。

---

**既知のリスクと逃げ道(要約)**: ① フックが特定タイトルで technically 実現困難と判明した場合 → OCR フォールバックを主経路に格上げし、精度改善(範囲指定 UI の使いやすさ、辞書拡充)に投資。② アンチチート誤検知が実利用で多発した場合 → ブラックリストの粒度を見直し、必要なら「導入タイトルは一律非対応」という保守的な方針に倒す。③ 翻訳コストが個人利用の想定を超えて肥大化した場合 → ローカルキャッシュ・辞書優先度を引き上げ、クラウド呼び出し頻度に上限を設ける。
