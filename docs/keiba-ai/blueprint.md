## 2. 設計思想(オマージュ元)

### 2.1 Benter型の二段構成

Bill Benter(1994年の論文 "Computer Based Horse Race Handicapping and Wagering Systems")の構成を骨格にする。

1. **能力モデル**: オッズ・人気を使わずに、各馬の勝率を推定する
2. **市場融合**: 能力モデルの勝率と、オッズから逆算した市場の勝率を、条件付きロジットで合成する
3. **賭け金**: 合成後の確率とオッズから期待値を出し、フラクショナル・ケリー(ケリー基準の一部比率)で配分する

X上の「人気・オッズを使わないAI」(FINAL8、カレンなど)は、1の能力モデルに相当する。2を持たないと、市場がすでに織り込んだ情報との差、つまり本当の割安を判定できない。

### 2.2 パイプラインを5工程に分ける

Valkyrie System の「予想・監査・圧縮・決裁・検証」の分離をそのまま採用する。工程ごとに入出力を固定し、どこで失敗したかを追えるようにする。

| 工程 | 役割 | 主な出力 |
|---|---|---|
| 予想(predict) | 能力モデル → 市場融合 → 全組み合わせの確率 | 馬ごとの勝率、組み合わせごとの確率 |
| 監査(audit) | 確率較正の確認、データ欠損・取消・馬体重異常の検知 | 「このレースは信頼できるか」の判定 |
| 圧縮(compress) | 全組み合わせから、期待値・点数・予算で候補を絞る | 買い目候補リスト |
| 決裁(decide) | 最終オッズ予測を当てて再評価し、買う/見送るを決める | 最終買い目、見送り理由 |
| 検証(verify) | 推奨時点・予測最終・確定オッズと結果を照合する | 成績ダッシュボード |

## 3. 予測ロジック

### 3.1 能力モデル

- 手法: LightGBM のランキング学習(LambdaRank)で、レース内の順位を学習する。出力をレース内ソフトマックスで勝率に変換する
- 特徴量の主な候補:
  - スピード指数(西田式の考え方: 走破タイムを距離・馬場で補正)、上がり3ハロン指数
  - 馬場: クッション値・含水率(JRAが公表)、当日の枠順・脚質の偏り
  - 血統×条件(距離・馬場・季節)
  - 調教(坂路・ウッドの時計)
  - 騎手・厩舎、乗り替わり、ローテーション(間隔・叩き何戦目)
  - 馬体重とその増減
- **レース条件別の有効ファクター**(奥野氏の思想): 芝/ダート、距離帯、クラス、開催場で特徴量の効き方が変わる。条件別のモデル、または条件を特徴量に入れた単一モデルの両方を試し、検証で選ぶ
- 特徴量の寄与(gain)は毎回記録し、条件別に比較する(カレン氏の運用)

### 3.2 市場融合

- 入力: 能力モデルの勝率の対数、単勝オッズから逆算した市場勝率の対数
- 合成: 条件付きロジットで重みを推定する(Benter方式)
- 券種別に重みを変える(つねくん氏の「馬券ごとに複数モデルの配合を変える」発想)。3連系では人気薄の評価が回収率を左右するので、単勝とは別に重みを学習する

### 3.3 組み合わせ確率(3連系)

- 基本: Harville式(単勝確率から2着・3着の条件付き確率を計算)
- 補正: Harville式は人気薄の2・3着確率を過小評価しやすい。Lo・Bacon-Shone、Henery、Stern などの補正を比較し、過去の3連単の実績で較正する
- 18頭立ての3連単は4,896通り。全通りを計算してから絞る

### 3.4 確率較正

- 指標: 対数損失(Log loss)、ブライアスコア、信頼性曲線(予測確率と実際の的中率の対応図)
- 監査工程で、較正のずれが基準を超えたレースは「見送り」にする(エンジニ馬氏の指摘への対応)

## 4. 臨機応変性: 最終オッズ予測

### 4.1 なぜ必要か

JRAはパリミュチュエル方式(売上を的中者で分ける方式)で、払戻しは**確定オッズ**で決まる。購入時に見えている期待値は、締め切りまでの資金流入で削られる。

X上のAI予想アカウントの多くは、前日や当日朝に推奨を無料公開している。その推奨に乗る資金は、締め切り直前に同じ馬・同じ組み合わせへ集まりやすい。自分のモデルが同じ馬を高く評価していれば、その割安は確定までに消える可能性が高い。

### 4.2 仕組み

| 機能 | 内容 |
|---|---|
| オッズ時系列の記録 | 開催日中、全券種のオッズを定期的に保存する |
| 最終オッズ予測 | 「現在オッズ・締め切りまでの残り時間・券種・人気帯・レース格」から確定オッズを予測する回帰モデル |
| 公開AI予想の重なり | 他者が公開した本命(◎)を手入力または取り込みで記録し、特徴量にする。重なる買い目は「削られる前提」で期待値を割り引く |
| 直前の急変検知 | 単勝・複勝の急なオッズ低下を「情報を持つ資金の流入」とみなし、勝率を上方修正する |
| 直前モード | 締め切り前は自動更新し、期待値が基準を超えた/割れた時だけ通知する |

- JRAの発売締め切りは発走2分前。運用は「発走10分前に候補提示 → 5分前に最終判断 → 手動購入」を目安にする
- **WIN5は直前判断が効かない**(締め切りが対象1レース目の発走前)。前日夜〜当日朝に点数配分を最適化し、キャリーオーバーの有無を期待値計算に入れる

### 4.3 オッズ履歴がない期間の扱い

過去の直前オッズの推移は、後から十分に入手できない可能性が高い(JRA-VANで取得できる時系列オッズの範囲は要確認)。対応は次の2段構え。

1. **記録は最優先で始める**。記録を始めた日からしか貯まらない
2. 記録が貯まるまでのバックテストは、確定オッズに「直前流入による目減り」を見込んだ割引を掛けて評価する。割引率は、自分の記録が貯まり次第で較正し直す

## 5. システム構成

### 5.1 Windows機が「開催日のみ稼働」であることへの対応

JRA-VANの公式データ取得部品(JV-Link)はWindows専用のため、**Windows機を「開催日の収集と配信の拠点」**とし、学習は平日に別マシンで行う。

| タイミング | Windows機の仕事 |
|---|---|
| 開催日の朝(起動直後) | 前回起動からの差分データを一括取得(出馬表・過去成績・調教・馬場)。翌日分の出馬表も取得 |
| 開催日の日中 | オッズの定期取得、馬体重・取消・発走時刻変更の取得。予測API・PWAの配信 |
| 開催日の夜 | 結果・払戻しを取得 → Parquet形式で書き出し → クラウドストレージに同期 → 終了 |
| 平日(Windows停止中) | なし。学習と検証は同期済みデータを使って別マシンで行う |

- 日曜の出馬表・枠順は土曜の時点で取得できるので、土曜夜に日曜分とWIN5の事前分析を行える
- スマホからは Tailscale などのVPNで、Windows機上のPWAにアクセスする。クラウドサーバーを常時借りる必要がない
- JV-Linkは32ビットのCOM部品のため、Pythonから呼ぶ場合は32ビット版Pythonなどの工夫が必要になる(実装時に要確認)

### 5.2 全体図

```
[Windows機・開催日のみ]
  JV-Link → collector(取得) → DuckDB / Parquet
                                ├→ 予想・監査・圧縮・決裁 API(FastAPI)
                                └→ PWA配信 ← スマホ(Tailscale経由)
  開催日夜 → Parquet をクラウドストレージへ同期

[学習用マシン・平日]
  Parquet → 特徴量生成 → 学習 → walk-forward検証 → モデル登録
  → 本番用モデルをWindows機へ配布
```

### 5.3 技術スタック(案)

| 層 | 選択 | 理由 |
|---|---|---|
| データ取得 | Python + JV-Link(COM) | 公式データ。スクレイピングに頼らない |
| 保存 | DuckDB + Parquet | サーバー不要で高速。Windows機と学習機の間でファイル同期だけで済む |
| 学習 | LightGBM、scikit-learn、Optuna | 実績が多く、軽い |
| 実験管理 | MLflow(ローカル) | 「検証用と本番用のモデル分離」と試行回数の記録 |
| API | FastAPI | Python資産をそのまま使える |
| UI | PWA(SvelteKit などの軽量フレームワーク) | 遷移が速く、ホーム画面に置ける。審査不要 |
| 説明・対話 | Claude API(`{{MODEL_ID}}`) | 数値の出力を説明文に変換。数値予測には使わない |

### 5.4 リポジトリ構成(案)

```
keiba-ai/
  collector/      # Windows専用。JV-Link取得、オッズ定期取得
  core/
    features/     # 特徴量
    models/       # 能力モデル、市場融合
    combos/       # Harville式と補正、組み合わせ確率
    market/       # 最終オッズ予測、急変検知
    optimizer/    # 圧縮・決裁(期待値、ケリー、予算制約)
  pipeline/       # predict → audit → compress → decide → verify
  app/
    api/          # FastAPI
    web/          # PWA
  verify/         # バックテスト、ダッシュボード
  data/           # gitignore対象
```

## 6. 検証の誠実さ(差別化A)

X上の開発者の最大の悩みは「改善したのか、過去に合わせただけなのか」(tohataha079氏)である。これを仕組みで防ぐ。

| ルール | 内容 |
|---|---|
| walk-forward検証 | 時系列順に「学習 → 次の期間で評価」を繰り返す。未来のデータで学習しない |
| 封印テスト期間 | 直近の一定期間は、モデル選びに一切使わない。最終確認で一度だけ使う |
| 予測時点の情報のみ | 確定馬体重・確定オッズ・確定人気など、予測時点で使えない情報は特徴量に入れない |
| 評価オッズ | バックテストは締め切り直前時点のオッズで評価する(履歴がない期間は4.3の割引) |
| 試行回数の記録 | モデルを何回試したかを残す。試行が多いほど「偶然良かった」可能性が上がるため |
| 検証用と本番用の分離 | モデル登録で、本番に出せるのは検証を通ったものだけにする(usugita氏の指摘) |
| 発走前の記録 | 推奨と見送りを発走前に自動で記録し、後から書き換えられないようにする(KEIBA TRACE、おにぃ氏の運用) |

### 毎回記録する項目

1. 推奨した時点のオッズ
2. 予測した最終オッズ
3. 実際の確定オッズ
4. 結果と払戻し
5. 見送った買い目とその理由

ダッシュボードでは「推奨時点の期待値」と「確定オッズでの実際の期待値」の差を表示し、**オッズ予測の外れ**と**確率モデルの外れ**を分けて確認する。

## 7. 買い目の最適化と予算

### 7.1 基本ルール

- 期待値 = 組み合わせ確率 × 予測最終オッズ。基準(例: 1.2以上)を超えた組み合わせだけを候補にする
- 賭け金はフラクショナル・ケリーで決める。3連単は的中間隔が長いので、1/8程度から始める
- 100円単位に丸める。丸めで期待値が下がる組み合わせは落とす
- 点数上限を設ける(例: 1レース30点まで)
- 構造はFINAL8氏の「馬券内候補8頭+境界線3頭」を参考に、軸・ヒモ・押さえの3層でフォーメーションを組む

### 7.2 予算枠(初期値の案。単位は未確定)

| 枠 | 上限の目安 | 使う条件 |
|---|---|---|
| WIN5 | 3,000円(30点) | キャリーオーバーがある、または期待値が基準を超えた時のみ |
| 3連系 | 7,000円 | 1レースあたり3,000円まで。期待値の基準を満たすレースのみ |
| 未使用分 | 持ち越さない | 「使い切る」ための買いを防ぐ |

**全レース見送りの日があってよい**ことを、仕様として明記する。

## 9. LLMの役割(差別化B)

| 用途 | 内容 |
|---|---|
| 根拠の説明 | 「なぜこの軸か」「なぜこの馬を消したか」を3行程度で示す。入力は数値と特徴量の寄与のみとし、LLMに予測させない |
| 見送り理由 | 「最終オッズで期待値が消えそう」など、見送りの理由も文章にする |
| 対話による条件指定 | 「予算5,000円、3連複中心で」を最適化の制約条件に変換する |
| テキスト情報の特徴量化 | 調教師コメント・乗り替わり理由などを、決まった分類に変換する |

競馬の参考書をRAG(資料検索)に使う案(まじてん氏)は、私的使用の範囲に限る。他者に配布しない。

## 11. リスクと対応

| リスク | 対応 |
|---|---|
| データ利用規約 | JRA-VANを正規契約で使う。netkeiba などのスクレイピングには頼らない。X投稿の自動取得は規約を確認し、当面は手入力 |
| 自動購入 | 当面は人が最終確認してIPATで手動購入。自動化は規約確認後に判断 |
| 過学習 | 6章のルールで防ぐ |
| 分散による資金枯渇 | フラクショナル・ケリーと予算枠。月次の損失上限を設定する |
| Windows機の停止 | 開催日の起動漏れを防ぐため、起動時に差分取得から自動で始まる構成にする |
